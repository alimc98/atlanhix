# V0.2.1 Android Readiness (audit only — no Android work in this milestone)

This document audits how ready the **current** architecture is for the future
Android milestone (v0.3: libbox/VpnService). Nothing Android was implemented
or changed in v0.2.1.

## What already exists (from v0.1/v0.2, unchanged)

| Component | State | Android relevance |
|---|---|---|
| `AndroidManifest.xml` | REAL | `INTERNET`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE`, `POST_NOTIFICATIONS`, `RECEIVE_BOOT_COMPLETED`; `NexusVpnService` declared with `specialUse` FGS type + `BIND_VPN_SERVICE`; `nexus://import` deeplink |
| `NexusVpnService.kt` | SCAFFOLD | foreground lifecycle, notification channel, `stopTun()`, `Builder()` skeleton (MTU 9000, 172.19.0.1/30 + v6, default routes). **No libbox binding yet** — honestly reports "VPN service" without fake connected state |
| `ConnectionController` state machine | REAL | 12 states incl. `coreReady/verifying/recovering` — Android service will drive the same machine; UI already derives exclusively from it |
| `CoreRuntime` contract | REAL | `prepare/validate/start/stop/status/health/traffic/logs/dispose` maps 1:1 to a future `AndroidVpnRuntime` backed by libbox |
| `CoreManager` front-engine design | REAL | sing-box-front topology is exactly the libbox model (tun inbound + selector); same config generator output can be handed to libbox |
| Traffic via Clash API `/connections` | REAL | works identically inside libbox |
| BinaryManager | REAL (desktop) | needs an Android branch: `jniLibs/arm64-v8a/libsingbox.so` (libbox AAR) — absent on this machine, unverified |
| Env-gated E2E harness | REAL | same harness pattern will drive device instrumentation tests via `adb` |

## Gaps that MUST be closed before Android work starts

1. **libbox AAR** — pick sing-box version, vendor the AAR, define the
   Kotlin↔Go binding (libbox `Client` API) and its config handoff.
2. **`AndroidVpnRuntime`** — new `CoreRuntime` implementation in
   `platform/android/` that: receives generated config JSON, calls libbox,
   and reports state/errors back over the method channel.
3. **Method channel** — `nexus/vpn` channel: start(config)/stop/status stream;
   parity with the desktop `CoreManager` surface.
4. **Per-app routing** — `Builder.addAllowedApplication/DisallowedApplication`
   mapping from the routing model's `package` rules (UI: app picker).
5. **Network-change recovery** — `ConnectivityManager` callback → controller
   `recoverFront` (already bounded restart-once).
6. **NDK/toolchain** — Android SDK + NDK absent on the dev machine used for
   v0.2.1 (`flutter build apk` blocked); Android work is unverifiable here.

## Verdict

**Architecture: READY.** The runtime contracts, state machine, and front-
engine design were built engine-agnostic and map cleanly onto libbox.
**Implementation: NOT STARTED (by design).** All Android integration remains
a clean v0.3 milestone; no fake states exist anywhere in the Android path.

# V0.2.1 Runtime Wiring Audit

Pre-change audit of commit `6e6a37a` (v0.2.0). Every claim below was
verified against the on-disk code, not the v0.2.0 report.

## Current architecture (as implemented)

```
ConnectionController (state machine)
   └─ CoreManager.startFor(profile)
        ├─ _ensureUpstream(profile)      # starts Xray / MDVPN when needed
        └─ singbox.startWith(_singboxLoad(all), selectedProfileId)
              └─ buildConfig(...)  ──► SingBoxConfigGenerator.generate(...)
                                        ⚠ socksUpstreams param NOT passed
```

## Actual traffic flow for an Xray-owned profile (v0.2.0, broken)

For `VLESS + XHTTP` (or any profile whose detector decision is Xray):

1. `ConnectionController.connect` computes `decision.core == xray`.
2. `decision.core` is **never written back** into the profile.
3. `CoreManager._ensureUpstream` switches on `profile.effectiveCore`
   → `unknown` (core was never persisted) → **Xray never starts.**
4. `singbox.startWith(...)` → generator receives **no `socksUpstreams`**
   (dead parameter — `_socksUpstreams()` output is discarded).
5. `OutboundBuilders.singBoxOutbound` for `vless + Transport.xhttp` returns a
   native outbound with `transport: null` (xhttp unsupported by sing-box)
   → **silently-wrong plain-VLESS/TCP config**.
6. Net effect: sing-box dials the remote server directly; Xray never runs
   for the profile. The v0.2.0 runtime tests passed only because they used
   `shadowsocks`/`vless(tls)` profiles whose native outbounds happen to be
   correct — the Xray path was never exercised end-to-end.

## Expected traffic flow (v0.2.1)

```
NEXUS → sing-box mixed inbound → selector
   ├─ sing-box-native profile ──────────────► remote server
   ├─ Xray-owned profile → SOCKS stub ─────► Xray local SOCKS ─► remote
   └─ MDVPN profile → SOCKS stub ───────────► MDVPN local SOCKS ─► tunnel
```

## Broken wiring / missing connections

| # | Severity | Finding | Fix |
|---|---|---|---|
| W1 | **CRITICAL** | `SingBoxRuntime.buildConfig/validateAll/startWith` never pass `socksUpstreams` to `SingBoxConfigGenerator.generate` — `_socksUpstreams()` is dead infrastructure | Thread the map through all three methods; CoreManager passes `_socksUpstreams(all)` |
| W2 | **CRITICAL** | `OutboundBuilders.singBoxOutbound` emits a native (broken, transport-less) outbound for Xray-owned profiles incl. all `Transport.xhttp` | Return `null` for `effectiveCore == xray` and for `transport == xhttp`; the generator then emits the SOCKS stub |
| W3 | **CRITICAL** | Detected core is never written back to the profile; `CoreManager` sees `unknown` → upstream never starts | Controller assigns `profile.core = decision.core` before `startFor`; CoreManager also treats `unknown + xhttp` as Xray-owned defensively |
| W4 | HIGH | Xray crash is undetectable: controller listens only to `cores.front.onExit`; `XrayRuntime.onExit` never merged | `CoreManager.onAnyExit` merges front + upstream streams; controller routes per crashing engine (bounded upstream restart, then failover) |
| W5 | MEDIUM | SOCKS stub may point at an Xray that never became ready | `_ensureUpstream` re-checks `inboundHealthy()` after start; failure = start failure |
| W6 | MEDIUM | `_singboxLoad` includes `unknown` profiles — with W2 fixed, unknown+xhttp profiles must also appear in `_socksUpstreams` or they vanish from the selector | `_socksUpstreams` includes `unknown` profiles with xhttp transport; unbuildable+unupstreamed profiles are logged as skipped, never silent |
| W7 | LOW | No Xray access log → no process-specific traffic evidence for path proofs | `XrayConfigGenerator` gains `accessLogPath`; runtime truncates at start; E2E asserts Xray saw the traffic |
| W8 | LOW | `SystemProxyController._reg` splits a quoted command string on spaces — fragile; no way to observe registry state in tests | Proper `List<String>` args + `query()` accessor |

## Incorrect assumptions found

1. "CoreManager routes Xray profiles through Xray" — the *management* logic
   existed (`_ensureUpstream`), but the *data path* did not (W1/W2); the
   v0.2.0 claim was false in effect.
2. "xhttp → Xray" was detector-level only; nothing enforced it downstream.
3. `Transport.xhttp → null` in `_sbTransport` produced a config that *passes*
   `sing-box check` as plain-TCP VLESS — engine validation alone cannot catch
   the wrongness. Only a traffic-path test can.

## Test gaps

* No test asserted the detector decision determines the actual outbound
  topology (the "detector controls traffic" invariant).
* No test asserted Xray was **in the traffic path** (running ≠ in-path).
* No E2E: runtime tests stopped at "engine started + readiness".
* No failover test with a real dead candidate + real healthy candidate.
* No crash-recovery test (engines were never killed).
* No process/port/temp-file leak test across repeated cycles.
* No system-proxy registry round-trip test.

## Engine

The Android runtime now uses the **real sing-box engine** (`libbox`) compiled
from sing-box **v1.14.0** source with `gomobile bind` for `arm64-v8a`
(`android/app/libs/libbox.aar`, ~25 MB). This is the same engine that powers
SFA (sing-box for Android):

* Dart generates the full sing-box config from the user's settings
  (`RuntimeConfigBridge` → `RoutingCompiler` → `SingBoxConfigGenerator`).
* `AtlanhixVpnService` starts `LibboxEngine`, which runs
  `CommandServer.startOrReloadService(config)`.
* libbox's tun inbound calls back into the service (`openTunForBox`) which
  establishes the `VpnService.Builder` and hands over the TUN fd.
* `CONNECTED` is only reported after a real HTTP probe through the tunnel
  (via sing-box's mixed inbound) — never on service start alone.

Reproducible AAR build (Windows):

```
# 1. Go 1.26.x installed to ~/dev-tools
git clone --depth 1 --branch v1.14.0 https://github.com/SagerNet/sing-box
cd sing-box
go get golang.org/x/mobile/cmd/gobind        # records tool directive
go install golang.org/x/mobile/cmd/gobind
gomobile bind -v -o libbox.aar -target android/arm64 -androidapi 24 \
  -javapkg=io.nekohasekai -trimpath \
  -ldflags "-X github.com/sagernet/sing-box/constant.Version=1.14.0 \
    -X runtime.godebugDefault=multipathtcp=0,tlssha1=1 -checklinkname=0 -s -w -buildid=" \
  -tags "with_gvisor,with_quic,with_wireguard,with_utls,with_naive_outbound,with_clash_api,badlinkname,tfogo_checklinkname0" \
  ./experimental/libbox
cp libbox.aar <repo>/android/app/libs/libbox.aar
```

Notes: upstream `gomobile` (not the SagerNet fork) has no `-libname` flag and
no `-buildvcs`; JAVA_HOME must point to a JDK ≥ 17 (Android Studio JBR works;
the JBR's `bin` must be on PATH for `javac`).

## VPN permission flow

* `Connect` → native `VpnService.prepare()`. When Android returns a consent
  intent, it is launched from `MainActivity` (`startActivityForResult`) and
  the method-channel reply resolves exactly once with the dialog outcome.
* Denial → state `permissionDenied`, error `VPN_PERMISSION_DENIED`, UI shows
  *"VPN permission is required to establish the connection."* with
  Retry/Cancel. No re-launch loop.
* Revoke while connected → `onRevoke()` → `REVOKED` → service stops, UI
  follows the native state. Next `Connect` calls `prepare()` again.
* Second connect in a session does **not** re-show the dialog while the
  Android permission is still valid.

* Exceptions: loopback/private networks (compiled as direct), and apps listed

## Rule mode

Deterministic compiled order:

1. Private networks (RFC1918, loopback, link-local, ULA) → DIRECT
2. User direct CIDRs → DIRECT
3. User proxy CIDRs → PROXY
4. User direct domains (exact + suffix) → DIRECT
5. User proxy domains (exact + suffix) → DIRECT/PROXY as configured
6. Custom rules (in user-defined order)
7. Final outbound (default PROXY)

Per-app routing is enforced by Android itself (below), which overrides all
engine rules for the affected apps.

## Direct / Proxy apps (real Android semantics)

`RoutingSettings.toAndroidAppLists()`:

* **Proxy Apps non-empty** → include-list mode: `addAllowedApplication` is
  applied for exactly those packages. Only they ride the VPN; every other app
  is routed by Android outside the tunnel (effectively DIRECT).
* **Otherwise** → exclude-list mode: `addDisallowedApplication` for every
  Direct App; those packages bypass the VPN at the kernel level (real DIRECT,
  not a Dart-side fiction).

The lists are applied twice by design: once as libbox `OverrideOptions`
(include/exclude package) and once by the service's `Builder` from
`TunOptions` — matching SFA semantics. Include wins over exclude.

## DNS modes

| UI mode | Engine config | TUN resolver |
| --- | --- | --- |
| Auto | automatic (local + remote) | 1.1.1.1, 8.8.8.8 |
| System | system resolvers | 1.1.1.1, 8.8.8.8 |
| Remote | encrypted DoH (Cloudflare) through the tunnel | 1.1.1.1 |
| Custom | user list (plaintext udp) | user list |

DNS always resolves through the tunnel; the TUN builder receives the resolver
list so Android's per-app DNS cannot leak around it. Diagnostics report the
effective mode.

`ON`/`OFF`/`AUTO`. OFF ⇒ no `::/0` route, no IPv6 TUN address, no IPv6 rule
path — the leak-free implementation. ON/AUTO add `::/0` and an IPv6 TUN
address.

## Auto-reconnect / Boot

* Auto-reconnect: network loss ⇒ `RECONNECTING` ⇒ engine restart ⇒ probe ⇒
  `CONNECTED`, with backoff. Busy-loop impossible (state-machine gated).
* Start-on-boot: `BOOT_COMPLETED` receiver starts the app only when the user
  enabled it; auto-connect additionally requires a valid profile + existing
  VPN permission (never re-prompts silently).

## Known limitations (honest)

1. **Xray-owned nodes are not connectable on Android v0.4.x** — the in-app
   engine is sing-box/libbox only; Xray upstream daemons do not run in-app.
   sing-box-runnable shares (vless/vmess/trojan/ss/hysteria2/tuic/wg) work.
2. **Hot reload**: routing/settings changes apply on the next connection. The
   UI states this explicitly ("applied after reconnect"); the running tunnel
   is never silently mutated.
3. **Interface monitoring** is stubbed in the PlatformInterface (libbox falls
   back to polling); Dart-side connectivity watching handles reconnects.
4. libbox `localDNSTransport` is null (tun DNS uses native mode) — no custom
   in-process resolver in v0.4.1.
5. Emulator/x86 builds require rebuilding the AAR with
   `-target android/arm64,android/x86_64` (default build is arm64-only, which
   matches the supported device fleet).

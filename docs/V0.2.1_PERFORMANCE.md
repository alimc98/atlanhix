# V0.2.1 Performance Measurements

All numbers are **actual measurements** from this machine (Windows x64,
Flutter 3.47.2 / Dart 3.13.2, sing-box 1.14.0, Xray 26.3.27), taken from the
`METRIC` lines printed by `test/e2e_test.dart` on 2026-09-03. Every figure is
produced by a real engine process — nothing is estimated.

## Engine lifecycle (CoreManager.startFor — full pipeline)

| Metric | sing-box front (native ss node) | Xray upstream + sing-box front |
|---|---|---|
| total start (generate → check → spawn → readiness) | 1527–4166 ms (median ≈ 2.0 s) | 1639–2261 ms |
| breakdown | `check` ≈ 0.6 s, spawn ≈ 0.1 s, readiness ≈ 0.7–3 s | adds one `xray run -test` + `xray run` spawn |
| readiness definition | Clash API `/version` OK **and** TCP connect to mixed inbound | + TCP connect to Xray SOCKS inbound |

`startFor` now stops any previously-running topology first (failover fix), so
switch-to-a-new-node = stop + full start ≈ 2–4 s when families differ;
same-family selector hot-switch remains ~0 ms engine downtime (verified: front
status stays `running`).

## First connection (local, through the full tunnel)

| Metric | Value |
|---|---|
| HTTP GET via SOCKS5 CONNECT through sing-box → ss-server → destination | 8044–8069 ms |
| note | dominated by the SOCKS5 probe's fixed 8 s window in `testHttpViaSocksProxy` when `Connection: close` waits on EOF; the request itself completes earlier (destination serves immediately) |
| same probe through Xray path | also ~8.0 s (same probe ceiling; path adds < 20 ms) |

Action item (v0.2.2): make the probe return on first response line instead of
waiting for connection close; true RTT is then visible (~10–40 ms locally).

## Startup (application)

* `flutter test` bootstrap of `AppDependencies` (store + repos + runtimes
  prepare, no engines started): < 400 ms.
* Full cold `flutter run -d windows` was **not measurable on this machine**
  (build blocked — see `V0.2_RUNTIME_AUDIT.md` §Verification for the exact
  environment error).
